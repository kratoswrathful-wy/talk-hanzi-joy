## 教訓與可沿用的做法

1. **診斷要以資料庫證據為準**：驗收方最初只驗證了「寫入有存進 DB」就推論讀取端漏查，實際是顯示規則的優先序問題。教訓：提出 bug 假設時，先把「顯示狀態的完整推導規則」查清楚（本案規則文件化於 B-7 §14.3–14.4），不要只驗證單一資料表。
2. **髒資料清單會漂移**：審核到執行之間系統持續使用，數字會變。條件式（而非固定 ID 清單）backfill＋執行前重新盤點＋漂移註記，是正確組合。
3. **雙向防護**：修「不得降級」時必須同時驗證「合法降級」（檔案重開）仍可運作，否則狀態會卡死。此案例已納入 Vitest。
4. **分階段審核有效**：schema 先審（放行 db push 前）、UI 後審、畫面驗收最後，三關分開讓每輪回饋都小而快。
5. **顯示層紅線寫進工單**：「匯出 diff 除譯文外為空」是可機器驗證的驗收標準，比「不要動匯出」的口頭約定可靠，已固化為 meta-export-display-safety.test.mjs。
